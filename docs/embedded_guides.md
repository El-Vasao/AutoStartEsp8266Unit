# Embedded guides (ESP8266)

Этот документ — сборник “правил выживания” под ESP8266. Он про причины, ограничения и практики,
которые держат проект стабильным на длинном аптайме.

## 1) Heap и фрагментация

### Проблема
ESP8266 имеет небольшую кучу, и она легко фрагментируется:
- частые мелкие аллокации/освобождения;
- `String` конкатенации;
- создание/удаление временных JSON документов.

### Правила
- в hot-path не используем `String` и динамические контейнеры;
- большие строки — только в `char[]` + `snprintf` и с фиксированными лимитами;
- JSON документы и payload — только через `PoolManager` слоты;
- если библиотека возвращает `String` (HTTP params, `Dir::fileName()`), держим его краткоживущим.

## 2) JSON (ArduinoJson)

### Почему нужен `PoolManager`
ArduinoJson умеет работать без heap, но только если мы заранее выделяем ёмкости.
Слоты решают сразу несколько задач:
- повторяемое выделение памяти без фрагментации;
- изоляция web/config/fs;
- предсказуемый ceiling на RAM.

### Правила
- для web API и SSE статус/лог — использовать слоты `WebApi`, `WebSse` и payload slots;
- для MQTT — лимиты `JsonBytes::Mqtt`, потоковый разбор команд и сериализация статуса в TX-буфер FSM (см. `src/mqtt/*`).

Если документ overflowed — это ошибка контракта (нужно либо ужать JSON, либо увеличить лимит осознанно).

## 3) Watchdog, `yield()` и `cooperate()`

### Два “типа” длинных операций
1) CPU-циклы без `delay()/yield()` → нужно отдавать управление SDK (`yield()`), иначе WiFi/lwIP и soft WDT страдают.
2) Потоковая запись/копирование (FS/OTA) → нужно кормить WDT, но не слишком часто (частый `yield()` иногда вреден).

### Практика
- в длительных циклах использовать `Core::cooperate()` (он троттлит `yield()` по времени);
- в потоковой сериализации/копировании — `ESP.wdtFeed()` “пачками” (см. `FSManager.Json.cpp`).

## 4) LittleFS: атомарность и “не забивать в ноль”

### Атомарность
Питание может пропасть в любой момент, поэтому запись должна быть “всё или ничего”:
- писать во временный файл рядом с целевым;
- затем commit (rename/replace) с учётом особенностей LittleFS.

### Свободное место
LittleFS деградирует при нехватке свободных блоков.
Правило: держим “зазоры” (`FSystem::*_MARGIN`) и при необходимости выполняем GC.

## 5) Асинхронный web и нагрузка на lwIP

Каждое SSE-соединение и очередь пакетов — это RAM.
Правила:
- ограничить `APConfig::MAX_CONNECTIONS`;
- ограничить `WebSseLimits::*` и не отправлять статус/лог бесконтрольно;
- дедуплицировать status по CRC и слать keepalive реже.
